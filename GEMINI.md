## What this is

SetEngine is an Electron desktop app (macOS / Windows / Linux) built **for DJs**. It does five things:

1. **Download** — paste a YouTube / YouTube Music or Spotify link (song, playlist, or album) and it downloads MP3s. There is **no embedded browser**; the link's source and shape are auto-detected from the URL.
2. **Set Extraction** — paste a YouTube DJ-set link and it produces the tracklist, then lets you download each track (or the whole set). It uses the uploader's published tracklist when there is one **and that list actually covers the set**, identifying the rest from the audio via Shazam and merging the two. **There is no engine choice and no API key anywhere in the app** — see "Song recognition" below.
3. **Set Maker** — analyze a folder of local audio (offline BPM + key detection), rate tracks, and build a harmonically-ordered setlist; import/export `.m3u`.
4. **Match Maker (TuneMatch)** — import a local library and get harmonic-mixing match suggestions for any selected track; detect + write missing BPM/key tags.
5. **Crate Sorter** — load one or more folders of local audio, pick destination folders ("crates"), then work through every track in alphabetical (filename) order with a seekable player and keyboard shortcuts, copying each into the crates you choose. Non-destructive (originals are never moved/deleted); no recognition or network needed.

It wraps the system-installed `yt-dlp` (YouTube) and `spotdl` (Spotify) binaries; `ffmpeg` does the audio conversion. Downloads run **unauthenticated** — there is no sign-in surface, so only public content is reachable. (Auth-gated YouTube content such as private playlists or age-restricted videos will fail; Spotify never needed a session because `spotdl` resolves public metadata + a YouTube audio match.)

## Getting Started (first-time setup)

```bash
# macOS / Linux — one command
npm run setup
# or: ./scripts/setup.sh

# Windows — one command
.\scripts\setup.ps1
```

The setup script checks for Node.js, installs npm dependencies, and verifies the
system tools SetEngine needs. It prints copy-pasteable install commands for
anything missing:

| Tool    | Required? | Purpose |
|---------|-----------|---------|
| yt-dlp  | **Yes**   | Downloads audio from YouTube |
| ffmpeg  | **Yes**   | Converts downloaded audio to MP3; decodes audio for BPM/key analysis |
| aria2c  | Optional  | ~2× faster downloads (multi-connection HTTP) |
| spotdl  | Optional  | Downloads from Spotify |

Once all required tools are green, run `npm start` to launch the dev build.

## Commands

Build / run is driven entirely by Electron Forge + the Vite plugin:

- `npm start` — Electron Forge dev: starts the Vite dev server, builds main + preload, launches Electron. Renderer changes hot-reload; **main-process changes need a full restart.**
- `npm run package` — produce an unpacked app in `out/`
- `npm run make` — installers per `forge.config.js` (Squirrel/Windows, zip/macOS, deb/rpm/Linux)
- `npm run publish` — Forge publish targets
- `npm run lint` — currently a no-op (`echo "No linting configured"`)

There is **no test framework** and no linter. The only mechanical check available is `node --check <file>` for syntax. Pure-logic modules (e.g. `set-maker.js`, `track-match.js`) are written as side-effect-free ESM so they can be exercised from a scratch script.

## Tech stack & build

- **Stock Electron** (`electron` ^42 from npm) — see "Electron runtime" below.
- **Electron Forge** (`@electron-forge/cli` ^7) with the **Vite plugin**. Three Vite builds: `src/main.js` (main), `src/preload.js` (preload), and the `main_window` renderer, configured by `vite.main.config.mjs` / `vite.preload.config.mjs` / `vite.renderer.config.mjs`. `package.json` `main` points at the built `.vite/build/main.js`.
- **Source is ESM** (`import`/`export`), compiled by Vite. Build config files (`forge.config.js`) are CommonJS; Vite configs are `.mjs`. `package.json` has no `"type": "module"` — don't rely on it; the Vite builds handle module format.
- **Runtime dependencies are deliberately few:** `electron-store` (settings; v11+ is ESM-only), `node-id3` (MP3 tag read/write), `p-limit` (concurrency caps), `electron-squirrel-startup` (Windows installer shortcut handling). Everything else (DSP, fingerprint signing, matching) is hand-rolled to avoid heavy/native deps.
- **Forge fuses** (`forge.config.js`): `RunAsNode` off, `OnlyLoadAppFromAsar` on, ASAR integrity validation on, cookie encryption on, Node CLI inspect/`NODE_OPTIONS` off. No Widevine fuse.

## External binaries — not bundled

`yt-dlp` and `ffmpeg` are **required system dependencies**. `aria2c` is optional but recommended (~2× faster downloads via multi-connection HTTP). `spotdl` is optional and only needed for Spotify links. All are auto-detected from `PATH`; if `aria2c` is present, yt-dlp downloads route through it, falling back automatically to the built-in downloader when aria2c fails (see `YtDlpWrapper` below).

`main.js` prepends `/opt/homebrew/bin`, `/usr/local/bin`, `/opt/local/bin` plus common pip/pipx/conda paths to `process.env.PATH` on startup (macOS/Linux). Without this, Electron processes launched from environments with a stripped PATH miss Homebrew/pip installs and detection incorrectly reports "not found". Keep this in mind when adding new external-binary dependencies.

The `yt-dlp-wrap` npm package is **not used** — `src/main/ytdlp-wrapper.js` spawns `yt-dlp` itself.

## Electron runtime — stock Electron

This app runs on **stock Electron**. It previously used the [Castlabs Electron](https://github.com/castlabs/electron-releases) fork for Widevine DRM, but that existed **solely** to play Spotify audio inside the (now removed) embedded browser. With downloads driven by pasted URLs there is no DRM requirement, so the fork was dropped — this also removed a recurring packaging failure (the `+wvcus` binary 404ing at package time). **Do not reintroduce the Castlabs fork or a Widevine fuse.**

`main.js` also sets `use-mock-keychain` + `password-store=basic` (so macOS doesn't prompt for keychain access — nothing sensitive is persisted) and, because the mock keychain can hang on graceful quit, the `before-quit` handler force-exits via `app.exit(0)` **after** killing child processes.

## Architecture

Three-tier Electron split with strict process boundaries via `contextIsolation`. **There is no embedded browser, no `WebContentsView`, no per-source Electron sessions, no `CookieManager`, and no DRM/Widevine init.** Downloads call the wrappers with `cookiePath = null`.

### Main process — `src/main.js` + `src/main/*`

`main.js` shims PATH, registers two custom schemes as privileged, wires the singletons, installs the protocol handlers, and delegates all IPC to `ipc-handlers.js`. The managers are constructed in `createWindow()` (after `app.whenReady()`), so anything that reads `app.getPath(...)` at construction is safe.

**Binary wrappers**

- **`YtDlpWrapper`** (`ytdlp-wrapper.js`) — the only module that spawns `yt-dlp`. Builds CLI args including `--extractor-args "youtube:player_client=default,web_safari,tv,mweb"` (SABR-resilient, cookie-compatible — `tv_simply` is deliberately *not* included because it gets skipped whenever `--cookies` is passed), `--concurrent-fragments 4`, and aria2c routing when available. Surface: `download()` (returns an EventEmitter: `progress` / `complete` / `error`, plus `cancel()`), `getVideoInfo(url, cookiePath, { withComments, timeoutMs, signal })`, `getPlaylistInfo()`, `getAudioStreamUrl(query)`, `searchMusic(query, limit)` (YouTube **Music** search), `searchYouTube(query, limit)` (general search), `searchSoundCloud(query, limit)`, `getHealth()`, `checkDependencies()`, `detectInstallMethod()`, `runAutomaticUpdate()`, `killAll()`. `withComments` adds `--write-comments` (top-sorted, capped) for the Set Extraction comment-tracklist pass; because that paginates a separate, slow endpoint, `executeJson` takes an optional **timeout + AbortSignal** and SIGKILLs the process — without them a stalled comment fetch hung an extraction job with no way to cancel it. `_flatSearch()` is the shared `--flat-playlist --dump-json` engine behind all three search methods (20 s timeout, filters out non-`Youtube` `ie_key` entries for the YouTube ones). It returns **`{ ok, entries }`**, and every search method returns **`{ ok, results }`** — the flag is load-bearing, because a throttled or timed-out search must not be mistaken for "this provider doesn't have the track". It used to resolve `[]` for both, which was harmless while YouTube was the only source and actively harmful once a fallback existed. SoundCloud is the one provider whose flat output is fully populated (title, uploader, duration), so its candidates carry `prefetched: true` and skip the verification fetch entirely. `translateYtDlpError` turns raw stderr into actionable messages for SABR, video-unavailable, private, age-restricted, members-only, and bot-challenge failures.

  **aria2c failures self-heal.** YouTube intermittently serves media URLs that aria2c can't handle — its range requests come back with a response it refuses to parse, surfacing as the opaque `aria2c exited with code 22`. It is video-specific, not universal (most videos download fine with identical args). Since aria2c is *only* a speed optimization, `download()` catches any `aria2c exited with code …` failure and transparently retries that track with yt-dlp's built-in downloader; after two such failures aria2c is disabled for the rest of the session. Note that classification reads **`err.stderr`, not `err.message`** — `translateYtDlpError` rewrites the message for humans, which erases the string the check needs (this was a real bug: matching on the message silently disabled the whole fallback).

- **`SpotdlWrapper`** (`spotdl-wrapper.js`) — the Spotify sibling of `YtDlpWrapper`. Same surface (`download` / `getHealth` / `detectInstallMethod` / `runAutomaticUpdate` / `getTrackInfo` / `getPlaylistInfo`) and the same EventEmitter shape on `download`, so `DownloadManager` doesn't branch on engine. `spotdl` resolves Spotify URLs to YouTube matches and downloads via yt-dlp/ffmpeg under the hood.

- **`filename-template.js`** — `sanitizeFilenameTemplate()` is shared by **both** wrappers so the same yt-dlp-style template (e.g. `%(artist)s - %(title)s`) produces identical, path-safe filenames. It preserves spaces/hyphens/commas/brackets but strips directory separators, `..`, and OS-illegal characters.

**Download queue**

- **`DownloadManager`** (`download-manager.js`) — queue as `Map<id, item>` where items are songs or playlists with `children: []`. **Queue concurrency is hardcoded at `MAX_CONCURRENT_DOWNLOADS = 5`** (sized to YouTube's per-IP soft threshold combined with `--concurrent-fragments 4`) — intentionally not user-configurable. Picks the engine per item's `source` (`spotify` → spotdl, else yt-dlp). Exports `isPlaylistUrl(url)` and `normalizeWatchUrl(url)` (strips a `list=` param from `/watch` URLs so YT Music album pages download as a single track), both built on `classifyUrl` from `sources.js`. Emits `download:progress` / `download:complete` / `download:error` / `download:queue-update`. **Main is the source of truth for status — the renderer must never override it** (we hit a bug where forcing `status: 'complete'` on every complete event masked real errors). The sanitized item carries per-item percent as **`progress`** (not `percent`).

**Set Extraction (the job system)**

- **`ExtractionJobManager`** (`extraction-manager.js`) — the source of truth for DJ-set extraction, modeled on `DownloadManager`. State is `jobs = Map<id, job>`; up to `MAX_CONCURRENT_EXTRACTIONS = 3` run at once via `pLimit(3)`, extras sit in `queued`. Each job owns a **private cache directory** `userData/ExtractionCache/<id>`. Surface: `addJob(url)` (validates via `classifyUrl`, fire-and-forgets `_run` through the limiter, returns `{ success, id }` immediately), `cancelJob(id)`, `deleteJob(id)` (cancels if running, then `rm`s the job's cache dir — this is the per-job song-cache deletion), `recordTrackDownloads(jobId, entries)`, `getJobs()`, `abortAll()`. Broadcasts `extract:jobs-update` (full sanitized list, structural changes) and `extract:job-progress` (one job, phase/percent ticks). **Job shape:** `{ id, url, title, status: 'queued'|'running'|'done'|'error'|'cancelled', phase, percent, tracks, engine, info, error, createdAt, cacheDir, trackDownloads, _abort }` (`_abort` is an `AbortController`, stripped before broadcast). **Jobs are in-memory and NOT persisted across restart** — `main.js` wipes the whole `ExtractionCache` root at boot (every on-disk subdir is then orphaned), and `before-quit` calls `abortAll()`.

- **`set-extractor.js`** — `extractSet(url, { ytDlp, settings, signal, onProgress, cacheDir })` is the per-job pipeline the manager runs: read info → resolve a published tracklist (chapters/description → MixesDB → comments) → **scan the audio unless the published list is proven complete** → merge → `dedupeTracks` (reusing `identityKey` from `track-merge.js`) → cache each track's download (at `settings.audioQuality`) into the job's `cacheDir`, keyed by `md5(identityKey(artist,title))`, resolving a YouTube URL via `resolveBestVideo`. **Requires `cacheDir`** (throws otherwise) and never wipes it — the cache is owned by the job (`deleteJob` / boot cleanup handle it). Only the scratch temp dir is cleaned in `finally`. Cancellable via the `AbortSignal`.
  - **A published tracklist no longer ends the job — this is the central design point.** It used to: `if (published) {…} else {downloadAndRecognize()}`. That made any parsed list the whole answer, and a comment headed *"My favourites for my own reference"* — 8 timestamps on a 2-hour set — became the entire 7-track output of a set Shazam could hear 73% of. The flow is now three-way: **complete** → published only; **partial** → published **plus** a full scan, merged; **none** → scan.
  - **The audio download starts immediately, in parallel with the published lookups.** Almost every path needs it now (a partial list gets supplemented, a complete one gets spot-checked), and when the tracklist only turns up in the comments — a pass that can take 90 s — the download is effectively free. Its progress is held back (`audio.reveal()`) until the published lookups finish, otherwise the phase readout runs backwards.
  - **The whole file is downloaded rather than slicing 12 windows remotely, and the reason is arithmetic, not capability.** ffmpeg *can* range-read a yt-dlp-resolved googlevideo URL — measured 12/12 slices, 512000 bytes each (exactly 8 s of f32 mono @ 16 kHz). It just isn't worth it: **12 remote slices cost 84 s against 118 s for the full 128 kbps download of the same 2-hour set**, so slicing saves ~34 s on the fast path and *wastes* 84 s every time the spot check contradicts and the full download is needed anyway. Download once, reuse for both the spot check and the scan. (An earlier measurement here was wrong and briefly justified this on the opposite grounds: two slice attempts timed out immediately after a 116 MB download had just completed — transient, most likely brief per-IP throttling — and were mistaken for ffmpeg being unable to reach googlevideo at all. A controlled retest against a single resolved URL succeeded every time.)
  - **A download failure is only fatal when there is nothing published to fall back on.** It is captured, not thrown, so a video that can't be downloaded but does carry chapters still produces a tracklist.
  - Returns `sparse` and `supplemented` alongside `tracks`/`engine`/`info`; `engine` becomes `published-<source> + shazam` when a partial list was topped up.

- **No recognizer factory, and no `recognizers/` directory.** There is exactly one engine, so `set-extractor.js` imports `shazam/recognize.js` directly. AudD and ACRCloud were removed wholesale — along with `getRecognizer()`, the engine picker, `retry.js`, `util.js`, every credential setting, and the `app:open-external` IPC that existed only to open their dashboards. **Do not reintroduce a keyed recognition service**; the requirement is that Set Extraction works with no account, no key and no per-request cost. All recognition HTTP runs in the main process, so the renderer CSP is unaffected. Nothing recognizes *every* track — unreleased IDs, bootlegs and heavily-effected sections defeat it, and the UI says so.

- **`track-match.js`** — `resolveBestVideo(ytDlp, query, title, artist)` turns an identified "Artist — Title" into a concrete YouTube video that has been **verified to be that recording**, returning `{ url, videoId, durationSec, title, artist }` or `null`. (`resolveBestVideoUrl` is a thin wrapper kept for callers that only want the URL.) Used by the extraction cache, `download:track` and `download:tracks`.
  - **Getting this wrong is the worst failure in the app**, because the caller then writes the *expected* tags onto whatever came back: right title, right artist, wrong audio, wrong cover. Measured on 55 real tracks from verified tracklists, the previous version returned a different recording **6 times (10.9%)**. It now returns 0.
  - **Two defects caused it, and they compounded.** (1) Title normalisation ran its feat-stripping regex to end-of-string, so the very common upload shape `Silva Bumpa FT. EVA - Body On Me` normalised to just `silva bumpa` — the title was deleted and the *correct* candidate failed the gate. (2) The artist was never actually checked: search runs `--flat-playlist`, which returns **only a title** (no artist, channel, album or duration), so the old "is the artist's name inside the candidate's title?" test could never fire on a YouTube Music result, and the code fell through to "accept the first title-passing candidate" — i.e. whatever YouTube ranked first. For "Body on Me" that was a different artist's song.
  - **Both upload shapes must be supported, and they carry the artist in opposite places.** An official "art track" has structured `artist`/`album` fields and a bare title; a fan upload has no structured metadata and puts the artist in the title. In the reported bug the *correct* answer was a fan upload with no artist field and the *wrong* one was an art track with a perfect one — so demanding structured metadata would actively prefer the wrong song. `artistAgrees` accepts agreement from any source: `artist`/`artists`/`creator`/`album_artist`, channel/uploader, the pre-dash part of the title, or the title text (a remix is credited to the remixer, so the original artist appears only there).
  - **Version identity is enforced in both directions.** Asking for `(ADULT Remix)` and getting `(Laurent Garnier Remix)` is a wrong file, and so is asking for the plain record and getting somebody's remix. `versionKey` ignores generic packaging (`Extended Mix`, `Radio Edit`, `Original Mix`) so ordinary labelling differences still match, and the comparison looks for the distinguishing tokens **anywhere in the title** because uploads often drop the brackets (`… Silver Screen Shower Scene ADULT Remix`).
  - **Nothing is accepted unverified.** Flat search only pre-filters and ranks; the chosen candidate's real metadata is fetched and must pass title, artist, version and duration. Duration also rejects the two things a title gate can't see — snippets (one match was 32 s) and long-form uploads (a track query returned `Boiler Room: Sheffield`). A separate **live/set guard** catches what duration can't: a single track lifted out of a live show is the right length and passes every other gate, but is still a different recording — measured, "WhoMadeWho live at Forum, Copenhagen 2024 - Tell Me Are We Feat Rampa" would have been downloaded in place of the studio version. Only unambiguous phrases count (`live at/from/in`, `boiler room`, `dj set`, `essential mix`); a bare "live" is far too common in real titles ("Living Sound", "Alive"). If the *request* names a live cut, a live upload is allowed. Verification is bounded (5 candidates, 60 s); running out of budget means unverified, which means **skip**.
  - **Providers are tried in quality order, and SoundCloud is the reason skips are rare.** YouTube Music → general YouTube → **SoundCloud**, stopping at the first verified match. SoundCloud is searched only when the first two fail, because that is exactly what it is for: bootlegs, edits, white labels, promos and remixes that were never released to a streaming catalogue and so genuinely are not on YouTube (measured: it carries "Traumer — Agenou (Y.M.O. Remix)" and "Candy Shop (Maddos x Falentin Bootleg)", neither of which YouTube has). Its flat search returns **full metadata** — title, uploader, duration — so those candidates verify with no extra fetch. It caps at **128 kbps**, which is why it is a fallback and not a peer, and why the UI badges any track sourced from it.
  - **A failed search is not an empty search, and conflating them broke this.** `_flatSearch` reports `{ ok, entries }` for that reason. During a heavily concurrent run, transient YouTube throttling made searches return nothing, which read as "YouTube doesn't have this track" and pushed **56 of 159 tracks** onto SoundCloud — tracks YouTube had all along, at worse quality. Each provider stage now retries once on failure before the next one is allowed to answer, and `set-extractor.js` caches at concurrency 3 rather than 5 to avoid provoking it.
  - **A last-resort fuzzy pass** re-examines already-gathered candidates tolerating a typo in the requested title (a real tracklist read "Indestructable" for Andy C's "Indestructible"). Metadata is cached from the strict pass so it costs nothing, and the artist, version and duration gates stay exactly as strict — only the title is loosened.
  - **The skips that remain are real.** They are recordings that exist nowhere as standalone files: compilation-exclusive edits ("Anjunadeep 13 Edit", "…Interlude Edit") that only exist inside the mix, plus the odd acappella or unreleased remix. Substituting the nearest version for those is exactly the correctly-labelled-wrong-file bug, so they are refused deliberately, and the UI says why.

- **`download-verify.js`** — the last line of defence, after the file is on disk. `verifyDownloadedAudio(path, { expectedDurationSec })` catches what a metadata gate cannot see: a truncated file, a format fallback, or a stale file picked up by the filename glob. Duration is the comparison because it's the one property known from the verified metadata and cheaply measurable on the result; tolerance is 12 s (encoders pad and round — a *wrong* track is essentially never that close by accident). A mismatched file is **deleted**, never left on disk under the requested name. Wired into `set-extractor.js`'s cache download and, via `addDownload`'s `expectedDurationSec` option, into `DownloadManager` — the option is opt-in, so ordinary Download-tab items (which have nothing to compare against) are untouched.

**Song recognition — how a tracklist is actually produced**

Set Extraction resolves a tracklist in two stages, cheapest first.

- **`tracklist-sources.js`** (pure, no I/O) — `parsePublishedTracklist(info)` reads a yt-dlp `--dump-json` payload and pulls a tracklist out of **chapters**, then timestamped **description** lines, then **comments**. When an uploader published one it beats the recognizer outright: correct remix names, correct spelling, exact start times, zero requests, zero cost — and `set-extractor.js` skips downloading the set entirely.
  - It **rejects** anything that doesn't look like a tracklist (< 3 entries, or accounting for < 10% of the runtime) so a video's navigation chapters can't silently replace a good recognition run.
  - **It also reports whether the tracklist is COMPLETE, and that is load-bearing.** A list can be entirely real and still describe a fraction of the set. `coverageOf()` sums `min(gapToNextEntry, 12 min)` over the entries — *what the list actually accounts for* — plus the head gap, max gap and min/track. `complete` is false when accounted < 65%, **or** the head gap > 8 min, **or** (max gap > 12 min **and** accounted < 90%). Max-gap is deliberately the weakest signal: Disclosure/Plitvice accounts for 93% of its runtime with one 15-minute gap and is complete. Measured — corpus chapter lists score 93–100% accounted with a 0 min head gap; the comment that caused this work scored **55% accounted, 25 min head gap, 32.6 min max gap, 15.1 min/track**.
  - **The old gate measured the wrong thing.** It asked `lastEntry.offsetSec / duration >= 0.4` — where the *last* entry sits, never how much is described. The 7-entry "my favourites" comment scored **0.97** on it.
  - **Runner-up comments are merged, not discarded.** Different listeners ID different tracks: on the same video the winning comment started at 43:00 while a second supplied `25:00 MPH - LA NYC` from the unlisted first half (Shazam independently confirmed it at 25:20), and a third resolved an `ID` placeholder to a real title. An entry is only added where the base list has nothing within 60 s, so two people timing the same track can't double it; a same-moment entry that *names* something the base wrote as "ID" replaces it. Capped at the top 5 comments. `stripCommentary()` then drops trailing prose brackets — "(unreleased, been waiting since 2021)" would otherwise go straight into the download search — while keeping anything naming a remix/edit/mix/feat, and anything under three words.
  - **Comments are parsed, and they matter more than expected.** Of **six** 1-hour-plus sets checked that published neither chapters nor a description tracklist (Solomun/Boiler Room, RÜFÜS DU SOL/Mayan Warrior, Miss Monique ×2, KOROLOVA, Regard), *all six* had a complete tracklist in a heavily-upvoted comment. Those are exactly the sets audio recognition does worst on. **Independently validated**: on every one of the six, a second, separately-written comment tracklist confirmed the chosen one entry for entry — 23/23, 19/19, 19/19, 18/18, 18/18, 17/17. Each candidate comment is parsed independently and ranked by entry count, then likes/pinned/uploader — a tracklist comment is long, densely timestamped and upvoted; chatter is none of those. It needs a second `--write-comments` yt-dlp pass (bounded by a 90 s timeout + the job's AbortSignal), so `set-extractor.js` only asks after chapters and description have both come up empty.
  - **The separator needs whitespace on only ONE side.** Requiring it on both dropped whole tracklists written `Janice STFU- Drake (Hills Remix)` (a 24-chapter set parsed as title-only and was then thrown out). Hyphenated names stay safe because in `Jay-Z` / `A-Ha` the dash has whitespace on *neither* side.
  - **Artist-less tracklists are accepted when a performer can be inferred.** A one-artist live set lists bare song titles (`Grown`, `Looped`, `Laced` for Kiasmos), which the 60%-must-name-an-artist gate rejected outright — throwing away complete, correct tracklists. Now, if the video title yields a performer (`Kiasmos live for Cercle at …`, `Armand Van Helden | Boiler Room: Miami`) and the entries are spaced like tracks rather than like section markers, the performer is attributed to every entry.
  - `Artist - Title` vs `Title - Artist` is undecidable from one line, so orientation is corrected **per entry** using bracketed mix/edit markers (an artist is never called "(Extended Mix)"). A list-wide majority vote was tried and is wrong — real uploaders mix both conventions inside one tracklist. Entries with no marker are left as parsed rather than guessed at.

- **`mixesdb.js`** — a fourth published source, and the only one that isn't the uploader or their audience. MixesDB is a community-curated wiki of DJ-set tracklists with a plain MediaWiki API. It matters because it covers the exact gap nothing else can: a set whose uploader published nothing **and** whose records aren't in Shazam's catalog. Set pages embed the source media links, so a set is found by **exact YouTube video id** (`insource:"<id>"`) rather than by fuzzy-matching a title like `2018-05-24 - Solomun @ Cercle, Théâtre Antique d'Orange` — exact or nothing, no false hits. Measured: found 5 of 6 corpus sets by id in **250–500 ms** each (against minutes for a comment pass and much longer for an audio scan), and 86% of the entries it returned were independently corroborated. Handles all three timestamp conventions in the wild (`[0:12:34]`, bare minutes `[12]`, none at all), strips the trailing `[Label - CATNO]` (labels use square brackets, remix markers use parentheses, so a trailing `[...]` is safe to drop), and skips `?` entries the same way `tracklist-sources.js` skips "ID - ID". Fail-soft; ordered **before** comments purely on cost.

- **`track-merge.js`** (pure, no I/O) — `mergeTracklists(published, recognized)` combines a partial published tracklist with a scan. **Published entries always win on overlap**: a human writes correct remix credits, correct spelling and `w/` blends, and names unreleased IDs no fingerprinter has. Recognition only ever *adds*. A recognized hit is dropped when its `identityKey` matches a published entry, or when it lands within 45 s of one with title containment ≥ 0.6 (Shazam indexes the same audio under several names, so identity alone misses aliases). Every row is tagged `source: 'published' | 'shazam'` for the UI. Also owns `identityKey` — imported back by `set-extractor.js` so dedupe and merge can't drift apart — and `spotCheckAgreement()`.

- **`shazam/recognize.js`** — the only recognizer, used whenever nothing was published **or the published list doesn't cover the whole set**. Needs **no API key, no account and no local catalog**. Fingerprints on-device and uploads only a ~250-character signature — the audio itself never leaves the machine. Owns probing, pacing and the adaptive scan; all the reasoning about results lives in `anchor.js`.
  - **It uses an unofficial, reverse-engineered endpoint.** That is against Shazam/Apple's terms, and it can break with no notice. This was a deliberate, informed choice — it is the only way to get "any song, no key, nothing to maintain". If it dies, Set Extraction degrades to published tracklists only.
  - **Use `net.fetch` from `electron`, never the global `fetch`.** Shazam's edge blackholes Node/undici connections (every request dies on a ~10 s connect timeout) while the identical request through Chromium's stack returns 200 in ~270 ms. This was a real bug: the fail-soft error path turned it into a silently empty tracklist. A total-failure guard now raises a real error instead.
  - **The scan is adaptive and proves its own coverage.** Seed a coarse grid, then repeatedly bisect the widest gap whose two ends do *not* prove the same record played across it (see `anchor.js`). A five-minute continuous track costs two probes; a dense run of transitions gets as many as it needs. This replaced a fixed "two probes per guessed segment" plan that measurably missed boundaries. `recognize()` accepts `seedObservations` so probes the spot check already paid for are reused, not repeated.
  - **`spotCheck(audioPath, { points })` is the safety net on a complete-looking published tracklist**, and it shares one probe path (`probeMoment`) with the full scan, so both are paced by the same machine-wide gate. Twelve evenly-spaced probes, ~43 s when nothing else is scanning. It also returns **`answered`**: a spot check that got no answer at all cannot contradict anything, so `set-extractor.js` leaves the published list standing rather than reading "no probe named a listed track" as a failed list. `spotCheckAgreement()` scores *of the probes that matched, how many named a track the list mentions anywhere* — **by title containment ≥ 0.6, never by identity**. Measured: exact identity scored a correct, complete Anjunadeep chapter list at only 44% (Shazam names the original release where the chapters name the "Anjunadeep 13 Edit") — too close to the failing set's 10% to be usable. Containment scores the corpus **73/78/82/100/100%** and leaves the failure at 10%. Below **50%** the list is treated as partial and the full scan runs; fewer than **3** matching probes is *inconclusive*, so the list is trusted — a set Shazam simply can't hear must not lose its good chapter list over it.
  - **Budget is one probe per 15 s of runtime, capped at 340.** Measured on a dense drum & bass set (64 tracks in 61 min, ~57 s each): going from one-per-25 s to one-per-15 s took recall **46.9% → 54.7%**, and precision went *up* (85.7% → 87.5%). More evidence never costs precision here, because acceptance is decided by whether the audio's timing agrees, not by how often a name appeared. Raising the cap is near-free on easy sets — the scan stops when coverage is proven rather than spending what it is given (that run converged at 230 of 300 available). Short track plays are what need the headroom, since a play must be seen twice to be proven at all.
  - **Rate limits, re-measured (the old figures were wrong).** 20 requests go through back to back in ~6 s, then 429. **Recovery is immediate** — the next request seconds later succeeds; the previously documented "~90 s clears a block" did not reproduce. A **3 s** gap sustained 34/34 clean. So a 429 costs a short pause and a retry of the *same* probe, not a 60 s cooldown, an abandoned probe, and a failed extraction after three of them. **The pacing that enforces this lives in `shazam/rate-gate.js` and is machine-wide, across processes** — see below.
  - **A throttled probe is *unheard*, not silent, and the difference is load-bearing.** `probeMoment` flags a moment every attempt of which was 429'd as `unheard`; `spotCheck` drops those from its observations and `recognize` keeps the point spent but never records it. Otherwise a 429 enters the scan as a no-match, and a no-match is read as **silence** — the one thing the bisection deliberately stops probing (`MIN_GAP_SILENT_SEC`). Rate limiting would quietly erase coverage instead of costing time. A run that is refused end to end (`answered === 0`) still raises a real error rather than returning an empty tracklist, and `MAX_CONSECUTIVE_UNHEARD = 3` stops a refusing endpoint from grinding through a 340-probe budget.
  - **`PROBE_SEC` is 8, and longer does not help.** On regions where 8 s returned nothing, 16 s and 26 s returned nothing on all 10 points tested. Longer windows also straddle transitions — at 12 s, two probes near a mix point returned the *neighbouring* track.
  - **There is no pitch correction, deliberately.** Re-sending a no-match resampled at ±3% and ±6% was measured across three unidentified tracks: it never recovered the right answer and returned a *different wrong* title nearly every time. It is a precision hazard, not a recall win.
  - **Known limits — and they are the dominant error source now, not the algorithm.** Measured over 5 real sets / 158 ground-truth tracks: **15% of tracks return nothing at any probe** (unreleased promos, white labels, exclusive comp edits, artists playing their own live re-edits) and **16% come back under a different name**, because Shazam's catalog indexes the same audio several times over via bootleg re-uploads. On one released track probed at 18 points, only 4 probes gave the correct title; the rest named three other "artists". Tripling probe density over six unidentified tracks recovered **none** of them — this is a catalog ceiling, not a sampling one.

- **`shazam/rate-gate.js`** — the machine-wide pacer every Shazam lookup passes through, and the reason parallel extractions stopped killing each other. Shazam's limit is per **machine**, but pacing used to be per **run** (`newProbeState()` held its own `lastRequestAt`), so the measured-safe 3 s gap was only honoured by a job running alone. Three jobs — the cap `ExtractionJobManager` allows — emitted a request every ~1 s, throttled one another, each counted its own 429s, and **all three died with "Shazam is rate-limiting this machine and did not recover"** (harness: 3 concurrent scans against a server modelling the measured limit — 20-request burst, one token back per 3 s — drew **35 × 429 out of 103 requests** under per-run pacing and **0 out of 57** through the gate). Now a single FIFO serializes slot *acquisition* only — lookups still overlap in flight, so one slow request can't stall the queue, but two never **start** closer together than the shared gap. A 429 is treated as information for the whole machine: it widens that gap (×1.6, cap 20 s) and parks a shared, jittered cooldown (4 s, doubling, cap 30 s) so everything backs off together — the only way a machine-wide block clears while several scans are running — then eases back after 8 consecutive clean answers. **The reservation is shared across processes** via `~/.setengine/shazam-gate.json` (mkdir-based lock, stale-tolerant, and fail-soft: any filesystem problem silently degrades to in-process pacing, never an error and never a hang). That matters because a second app instance, or `scripts/eval` probing from a plain node process, is invisible to an in-process queue and perfectly visible to Shazam, which sees one IP — verified: two independent node processes interleave at exactly 3 s. Concurrency now costs *time* (N scans share one request stream) instead of *failures*. **Any new Shazam request path must go through `acquireShazamSlot()`.**
- **`shazam/anchor.js`** (pure, no I/O) — everything that decides *what the probes mean*. **This is where the accuracy came from**; read it before touching recognition.
  - Shazam returns `matches[].offset`: where inside the reference recording our sample matched. While a record plays, that position advances in lockstep with wall clock, so for two probes of the same record `rate = Δoffset/Δt` must be ≈ 1 and `anchor = t − offset` must be constant. Measured: a genuine play holds its anchor to ~10 ms across a 30 s gap. A false match can't fake it — it is pinned to whichever section of its own reference resembles our audio, so measured false runs came back at rate **−0.31, −0.07 and +0.05** (reference position standing still or running backwards while the mix moved on).
  - **This replaced score thresholds entirely.** The old model scored 70 for one sighting and 95 for two and let the user threshold it — but corroboration endorses a *repeatable* error exactly as readily as a truth. Measured on one set: 11 of 12 single-sighting tracks were junk, and a wrong track scored 95. Rate agreement is a physical claim about the audio, not a popularity count.
  - **Two tiers, and the looser one is load-bearing.** PROOF (anchor essentially constant) is strong enough to assert continuous play — used for coverage and for deleting contradicted sightings. LINK (rate merely plausible) groups sightings, and is needed because repetitive club records are **loop-ambiguous**: on "ARTBAT — Upperground", probes 38 s apart returned offsets 121.0, 116.6, 173.8, 380.8 — the anchor scatters by 73 s, yet the aggregate rate is +1.24 while junk stays near 0. Grouping on PROOF alone tore that real play into four fragments and discarded all of them.
  - **`dropContradicted()` replaces the old `dropEnclosed()`.** Same goal — a sighting inside a stretch another record demonstrably owns is a misread — but the old version compared only a candidate's first and last sighting, so a track spotted once early and once late spanned the entire set and deleted every one-sighting track between. Now the encloser must have two sightings that hard-prove against each other, one strictly each side of the sighting being judged.
  - **The anchor is also the track's real start time**, far better than "the first probe that happened to hear it" — clamped, because DJs cue in mid-record so the raw anchor can precede the audible entry.

- **`shazam/signature.js`** — the only file that touches `shazamio-core` (zero-dependency WASM). Loaded via `createRequire`, deliberately: the package is CommonJS *and* a runtime require is invisible to Vite, so it is never bundled — which matters because its loader reads its `.wasm` relative to `__dirname`. **No `vite.main.config.mjs` change is needed; don't add one.**

> **`segmenter.js` is gone.** It planned probe points offline from a spectral novelty curve. The adaptive scan supersedes it: novelty guessed where transitions *might* be (measured: 5 of 10 found) and spent a fixed budget there, whereas bisection-to-proof spends requests only where coverage is genuinely unproven. Don't reintroduce it.

**Offline analysis & tagging (Set Maker / Match Maker)**

- **`audio-analyzer.js`** — spawns `ffmpeg` to decode a file to mono Float32 PCM @ 22.05 kHz, then computes band balance (bass/mid/high), spectral brightness, and intro/outro length from an RMS-envelope walk. No WASM/native analysis lib.
- **`key-bpm-detector.js`** — fully-offline BPM + musical key estimation from the same decoded PCM: dual-band onset envelope → autocorrelation × comb-filter tempogram for tempo (returns candidate metrical levels), tuned chromagram → Krumhansl–Kessler correlation for key (Camelot + name). Shares the `dsp.js` FFT/Hann helpers.
- **`dsp.js`** — size-parameterized FFT + Hann window, used by the analyzer and detector.
- **`bpm-sources.js`** — free, keyless **Deezer** cross-check for detected BPM (`lookupBpm`, fail-soft) plus `reconcileBpm` consensus logic that resolves octave/half-time errors; also exports the `cleanTitle` / `primaryArtist` text helpers reused by Set Extraction. The cross-check **always runs** (no longer user-toggleable).
- **`set-maker.js`** — pure, IPC-free harmonic-mixing algorithm: Camelot key distance, half/double-time-aware BPM distance, move-type scoring, and a 2-opt tour optimizer. `buildSet(tracks, opts)` orders a library; `rescoreTour(tracks)` recomputes transitions after a manual edit.
- **`rating-writer.js`** — `writeRating` / `readRating` (MP3 ID3v2 POPM byte **and** a `[★★★★]` COMM marker so Serato shows it; native comment field via ffmpeg remux for M4A/FLAC/OGG/Opus/AAC) and `writeBpmKey` (writes detected BPM/key back into the file's tags).

**Settings, sources, streaming**

- **`SettingsManager`** (`settings-manager.js`) — `electron-store` wrapper (v11+ ESM-only). `concurrentDownloads` is **deliberately not in the schema** (queue concurrency is hardcoded; exposing it just lets users pick rate-limiting values). Default `downloadFolder` resolves to `app.getPath('music')` at construction. There are **no credential settings at all** any more; the constructor also runs a one-time delete of the keys left behind by the removed engines (`recognizer`, `auddApiToken`, `acrHost`, `acrAccessKey`, `acrAccessSecret`) so a stale API key doesn't sit in a plaintext JSON file forever. See "Settings keys" below.
- **`sources.js`** — URL-classification + registry. `classifyUrl(url)` returns `{ source: 'youtube-music'|'spotify', kind: 'track'|'playlist', id? }` (or `null`), used by `DownloadManager`, `ExtractionJobManager`, and the `url:classify` IPC. The `SOURCES` registry holds `{ id, label, downloader }` per source.
- **`stream-resolver.js`** — `handleStreamRequest(req, ytDlp)` backs the `setengine-stream://` protocol: it base64url-decodes a search query, resolves it to a direct YouTube audio URL via `ytDlp.getAudioStreamUrl()` (50-minute in-memory cache), and proxies the bytes with Range support — for previewing remote audio without downloading.

Populated **only** inside the dialog-backed `sorter:*` IPC handlers — the renderer can't inject a path.
- **`audio-files.js`** — one definition of "what counts as an audio file" (`AUDIO_EXTS`) and one recursive `walkAudioDir`, shared by Match Maker's library scan and the Crate Sorter's source folders.

**IPC** — `ipc-handlers.js` registers everything (see "IPC channel reference" below). `download:url`, `download:retry`, `download:track`, and `download:tracks` pass `null` for cookies (unauthenticated). `safeOutputDir()` there normalizes a renderer-supplied destination folder (expands `~`, requires an absolute path, else `null` → caller falls back to the configured folder). **Add new IPC here**, and expose it through the preload bridge.

### Preload — `src/preload.js`

Single source of truth for the renderer ↔ main contract. Every channel is exposed via `contextBridge` as `window.setengine`. **`on*` event subscribers return an unsubscribe function** — preserve this pattern when adding events so callers can clean up. Examples: `classifyURL(url)` validates a pasted link before queueing; `getExtractionJobs()` + `onExtractJobsUpdate` / `onExtractJobProgress` drive the Set Extraction page.

### Renderer — `src/renderer.js` + `src/renderer/*`

Vanilla JS, no framework, imperative DOM (no templates). `src/renderer.js` imports the global stylesheet and boots `App`. `App` (`renderer/app.js`) is a tiny page router: `PAGES` map → `new PageClass(this)` → `.render(container)`; pages may implement `.destroy()` for teardown, and stash state on the `app` singleton (e.g. `app.matchState`, `app.setMakerState`, `app.extractState`) so navigating away and back is cheap. `App.setupIpcListeners()` forwards realtime **download** events to the current page **only when it's the queue page** — pass `data` through unchanged, never override `status`.

**Pages** (`renderer/pages/*`):
- **`download.js`** — the landing page. One text box takes any YouTube / YouTube Music or Spotify link; Enter or DOWNLOAD classifies it via `classifyURL`, rejects unrecognized links, runs a just-in-time check that `spotdl` is installed for Spotify links, then calls `downloadURL`. The **destination folder lives on this page** (`.folder-display` + BROWSE, which persists `downloadFolder`). Input clears after queueing; a button jumps to the Queue.
- **`queue.js`** — the download queue: per-item status badges (queued/downloading/complete/error/cancelled), a source badge (YT / SPOTIFY), playlist children, cancel/retry/clear. Driven by `download:queue-update` + the per-item events.
- **`extract.js`** — **Set Extraction, as a job list + detail.** The list view has the URL box + EXTRACT (start several; they run in parallel) and one card per job (status dot, live phase/percent, delete ✕). Clicking a card opens the detail (tracklist, destination folder, per-track play/download, DOWNLOAD WHOLE SET → writes the files). Main is the source of truth: the page mirrors `getExtractionJobs()` and patches from `onExtractJobsUpdate` / `onExtractJobProgress`. **Navigating away does NOT cancel a job** — `destroy()` only unsubscribes, tears down audio, and stashes `{ view, selectedJobId, folderPath }`. Per-track downloads pass `jobId` + `trackIndex` so the ✔/progress state (stored on the job's `trackDownloads`) survives navigating off and back. `SOURCE_LABELS` names each published source distinctly (they don't carry equal authority); `parseEngine()` splits `published-<source> + shazam`, and on a **merged** tracklist only, each row gets an origin badge (`.extract-row-origin`) saying whether a person named it or Shazam heard it — on a single-source list that badge would be noise. `job.sparse` adds a plain-language note that some tracks (unreleased dubs, white labels) can't be named by anything.
- **`setmaker.js`** — **Set Maker**, three views in one page (library / rate / setlist): analyze a folder of local audio (BPM/key), star-rate tracks, then build a harmonically-ordered setlist via `setmaker:build`; import/export `.m3u`. Missing BPM/key can be detected and written back (`tags:detect-and-tag`).
- **`match.js`** — **Match Maker (TuneMatch)**: import a local library, pick a track, and get harmonic-mixing match suggestions filtered by a BPM threshold; dedupe; detect + write missing BPM/key tags for path-bearing imports.
- **`sorter.js`** — **Crate Sorter**, two views in one page (setup / sort). Setup: "Add folder(s)" (multi-select source folders, each scanned recursively for audio) + "Add folder(s)" destination crates. Sort: a left sidebar lists every song (filename-alphabetical, numeric-aware) with per-song status (pending / current / sorted / skipped / missing) and is clickable to jump back and re-sort; the main pane has a seekable player (a bare `new Audio()` **independent of the DOM**, so a re-render on toggle doesn't interrupt playback) plus a crate-toggle grid. Advancing **commits**: copies the file into each newly-selected crate via `sorter:copy-into-folders` (idempotent — already-copied crates lock as "COPIED"; advancing with nothing selected = skip). Keyboard: Space play/pause · ←/→ seek 5s (Shift 15s) · 1–9 toggle crate · Enter/↓ next · ↑ previous · Esc pause. State (songs / crates / index) is in-memory only, stashed on `app.sorterState`; **not persisted across restart**.
- **`settings.js`** — the "use the uploader's tracklist" toggle, `recognizerMinConfidence`, audio quality, filename template, and the yt-dlp / spotdl version + accelerator readout. Nothing on the page is conditional any more (one engine, no credentials), so `attachListeners()` is empty and there is no `syncRecognizerFields`. The destination folder is **not** here — it lives on the Download page.

### Custom protocols (`main.js`)

Both schemes are registered privileged (`standard`, `secure`, `stream`, `supportFetchAPI`) before `app.whenReady`, and both appear in the CSP `media-src`:

- **`setengine-audio://local/<base64url path>`** — serves a **local** audio file with proper HTTP **Range** support (so the audio element can seek, and so M4A files with a trailing `moov` atom load at all — see the long comment there). Access is restricted to files under the user's music / downloads / home directories **plus any directory the user explicitly picked this session via the Crate Sorter dialogs** (tracked in `session-roots.js` — this is what lets a Crate Sorter library on an external drive be previewed). Used for previewing cached/extracted/library tracks (Set Extraction, Set Maker, Match Maker, Crate Sorter). - **`setengine-stream://<base64url query>`** — proxies a yt-dlp-resolved **remote** YouTube audio stream (via `stream-resolver.js`) for preview without downloading.

### CSP

`index.html` Content-Security-Policy: `default-src 'self'`, `script-src 'self'`, `img-src 'self' data:`, `style-src 'self' 'unsafe-inline' https://fonts.googleapis.com`, `font-src https://fonts.gstatic.com`, `media-src 'self' blob: setengine-audio: setengine-stream:`. ## Health & auto-update

`YtDlpWrapper.getHealth()` returns `{ version, outdated, recommendedMin, aria2c }`. `MIN_RECOMMENDED_YTDLP` (currently `2025.09.05`) is a constant at the top of `ytdlp-wrapper.js` — **bump it as new SABR-class breakages emerge.** The startup modal in `app.js checkYtDlpHealth` prompts when `outdated: true`; click-through runs `runYtdlpUpdateFlow()` (`renderer/tool-update.js`) → `ytdlp:update` IPC. `SpotdlWrapper` mirrors this (`MIN_RECOMMENDED_SPOTDL`, `spotdl:health` / `spotdl:update`), surfaced on Settings and via the Download page's just-in-time check rather than a startup nag.

`detectInstallMethod()` distinguishes Homebrew / pipx / pip / standalone via `brew list --versions` and shebang parsing of the binary. `runAutomaticUpdate()` runs the matching command:
- Homebrew → `brew upgrade <tool>`
- pipx → `pipx upgrade <tool>`
- pip → `<detected python> -m pip install -U <tool>` (with PEP 668 `--break-system-packages` retry)
- Standalone → `yt-dlp -U` (yt-dlp only; spotdl standalone has no self-update)
- Missing → throws an "install it first" error

The Settings page shows `yt-dlp <version>`, `spotdl <version>`, and `Accelerator: aria2c (active)` / `Accelerator: built-in. Install aria2 for ~2× faster downloads`.

## Conventions & gotchas

- **Main is the source of truth.** `DownloadManager` and `ExtractionJobManager` own state and broadcast it; the renderer mirrors and patches, never overrides `status`. Forcing renderer-side status has masked real errors before.
- **Main-process changes need a full `npm start` restart** (renderer hot-reloads).
- **Sanitized download items carry percent as `progress`, not `percent`.** Reading the wrong field pins rows at 0%.
- **Preload `on*` must return an unsubscribe fn**, and pages must call them in `destroy()`.
- **Per-track download state uses sentinels:** `copied-<i>` (served from cache) and `skipped-<i>` (no confident match). For Set Extraction these live on the job's `trackDownloads` map in main; real download ids resolve against the live download queue.
- **`resolveBestVideo` returns `null` to mean "skip"** — never substitute a guessed URL, and never accept a candidate whose real metadata hasn't been checked. A wrong file is far worse than a missing one here: the caller stamps the *expected* title and artist onto whatever it gets, so a bad match ships as a correctly-labelled wrong recording that only the cover art gives away. Measured, that happened on 10.9% of tracks before verification existed.
- **A download is not finished until it has been verified.** `download-verify.js` re-checks the file on disk against the duration of the recording that was verified, and deletes it on mismatch. If you add another download path for identified tracks, wire it through the same check — pass `expectedDurationSec` to `addDownload`.
- **A failed provider search must never read as "this provider doesn't have it."** Every search returns `{ ok, results }`; treat `ok === false` as unknown and retry, never as empty. Getting this wrong silently reroutes tracks to a lower-quality fallback — it cost 56 of 159 tracks once. The same rule applies to any provider added later.
- **When adding a download source:** it only needs to be something yt-dlp can both search and download; the download path needs no changes at all (`ytDlp.download()` took a SoundCloud URL unmodified). Return the same `{ id, url, title, … }` shape from a `searchX` method, set `prefetched: true` if the flat output is complete enough to verify without a second fetch, and put it *after* the higher-quality sources in the stage list in `track-match.js`. **Beatport is not viable** — it is Cloudflare-protected (403 to both plain requests and yt-dlp's extractor) and only ever serves 30–120 s store previews, so it could not supply a full track even if reachable. Bandcamp has no yt-dlp search and both of its public autocomplete endpoints are dead.
- **Crate Sorter copies, never moves.** `sorter:copy-into-folders` is non-destructive (skip-if-identical, else ` (n)` suffix; never overwrites). Its state is in-memory only (`app.sorterState`), not persisted across restart. Previewing source files outside Music/Downloads/Home relies on `session-roots.js` — a path is only ever allow-listed from inside a dialog-backed `sorter:*` handler.
- **Recognition is the cheapest source's backstop, not its replacement.** `set-extractor.js` tries chapters and description, then **MixesDB** (one fast API call, matched by video id), then a second yt-dlp pass for **comments** — each step cheaper *and* more accurate than the next. But finding a tracklist no longer ends the job: it must also be **complete**, or the audio is scanned and the two are merged.
- **"Parsed" is not "finished" — never treat a published tracklist as the whole answer without checking coverage.** This is the single most damaging bug this feature has had. A partial list is *more* dangerous than no list, because it short-circuits everything downstream and looks like a success: 7 hand-picked comment entries stood in for a 2-hour set whose audio Shazam could identify at a 73% probe hit-rate, and it also silently cancelled ~30 track downloads. If you add a tracklist source, it must report completeness (`completenessOf()`) and it must be allowed to be supplemented. `complete: false` does **not** mean "bad" — those entries are still the best-named ones you have.
- **No single tracklist source is trustworthy on its own — including the uploader's.** Measured across three sets with all three sources available, the chapter list was corroborated by another independent source only 92.6% of the time, MixesDB 86.3%, audio 84.9%. A real example: the chapters say "Bijou Williams — Silver Fist" where *both* MixesDB and the audio say "Chicago 72". That is why evaluation of recognition changes must never treat one source as ground truth — scoring the recogniser against chapters alone understated it by about 10 F1 points. Cross-source consensus is deliberately **not** fused into the shipped output: measured, it would have added exactly one corroborated row across three sets while introducing a conflict-resolution policy and a new class of bug.
- **Shazam's recognizer must use `net.fetch`, not global `fetch`** (see above). Its rate limit is measured, not guessed: ~20 burst, **3 s sustained is clean**, and a 429 clears within seconds — so retry the same probe rather than abandoning it. Lowering `BASE_GAP_MS` (in `shazam/rate-gate.js`) below ~2 s will start drawing 429s.
- **Shazam pacing is per *machine*, not per job and not per process, and it must stay that way.** The limit is per machine, so any per-run gap is multiplied by however many scans are running — which is exactly how three parallel extractions came to fail each other with "Shazam is rate-limiting this machine and did not recover". Every lookup goes through `acquireShazamSlot()` in `shazam/rate-gate.js`, and the reservation is shared with other SetEngine processes through `~/.setengine/shazam-gate.json`. A 429 must be reported to the gate (`noteShazamRateLimited()`) so everything backs off, never handled with a local sleep. Raising `MAX_CONCURRENT_EXTRACTIONS` does not raise Shazam load — it only splits the same stream more ways.
- **Don't judge a recognition result by how many times a name came back.** That is what the old scoring did and it is exactly the failure mode: section-locked misreads repeat, so they corroborate. Judge it by `anchor.js` — does the position inside the reference recording advance at rate 1? A name seen twice with an inconsistent anchor is weaker evidence than a name seen twice with a constant one.
- **When adding a source:** add a `sources.js` entry + wrapper module + `DownloadManager` wiring (it already dispatches on `item.source`).
- **When adding IPC:** register in `ipc-handlers.js` **and** expose in `preload.js`; if it's an event, return an unsubscribe fn.
- **Adding a remote origin** (image/script/font) requires editing the CSP in `index.html`.
